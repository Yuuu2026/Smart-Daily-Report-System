# 项目讲解脉络（给别人介绍时照着说）

> 用途：课程汇报 / 组内分享 / 面试讲解。先讲边界，再讲一条主线，最后讲取舍与坑。
> 全文按「能被追问」的方式组织：每个说法后面都能指到具体文件。

## 零、大白话版（先讲这个，对方听不懂代码也能跟上）

**一句话**：这是一个"替人写日报的机器人"——把大家散在 GitHub 和群聊里的动静捡回来，
人只补两句话，它自动整理、发邮件、挂到网上，还顺手画一张工作量柱状图。

**它其实只有三段：收 → 补 → 发。**

- **收**：去两个地方拿东西（GitHub 提交、飞书群聊）；拿回来先过筛子，同一条只留一份，放进一个"账本"。
  账本就是这台电脑上的一个数据库文件。
- **补**：人要登录，看着今天的原料写两句话（解决了什么问题 / 下一步做什么）。写太空泛（比如"改了代码"）
  会被提示补细节；写完按段落存进账本，顶部那张柱状图会跟着变高。
- **发**：点一次发布，同时做三件事——记进账本、给负责人发一封邮件、更新展示页；
  再自动同步到公网那个只读网页。

**代码用"小店铺"打比方**

| 角色 | 文件 | 大白话 |
|---|---|---|
| 前台 | `publisher_app.py`（5001 端口） | 要刷工牌才能进，只负责收话、传话 |
| 展示窗 | `app.py`（5000 端口） | 谁路过都能看，只能看不能改 |
| 后厨 | `publisher_repo.py` | 真正干活：从账本取、往账本写 |
| 采购 | `github_source.py` / `feishu_source.py` | 两家供货商，接口不同但按同一规格交货 |
| 账本 | `daily_report.db` + `uploads/` | 一个数据库文件 + 一个存照片的文件夹 |
| 配送 | `email_notifications.py` + `export_static_site.py` | 送邮件、送公网网页 |

**三个"为什么"，都能用一句人话答**

1. 为什么要两个端口？——一个当展示窗（不能改）、一个当前台（要登录），权限一眼清楚。
   代价是两个进程都得看着，所以有了值班员。
2. 为什么只用一个数据库文件？——十来个人用，不值得架服务器；缺点是只能在这台电脑上跑。
3. 为什么采购单独一层？——GitHub 和飞书接口完全不一样，把差别关在采购部，后厨和前台不用改。

**谁在看着它别死**：一个不弹窗的"值班员"程序（`scripts/web_supervisor.py`），每 30 秒看一眼
两个网站和 GitHub 的连接助手，谁躺下就扶起来；它自己登录时启动一次，没有窗口。


## 一、30 秒开场

这是一个给 5–15 人小团队用的日报系统。成员不用手写日报：系统从 GitHub 提交和飞书群聊里把当天的工作自动收上来，
成员只补两句话（解决了什么问题 / 下一步做什么），点一次发布，团队归档页和公开链接立刻更新，
负责人同时收到一封带工作量柱状图的邮件。整套东西跑在一台普通 Windows 电脑上，没有云服务器，也不需要运维。

三句话记住它：**数据自动收、内容人工补、结果双出口（本机页面 + 公网静态站）**。

## 二、先划边界：两个端口 = 两种权限

| 端口 | 文件 | 定位 | 能不能写 |
|---|---|---|---|
| 5000 | `web/app.py` | 团队归档页，投屏/给老师看的那种 | 只读（写接口已下线，返回 410 或重定向） |
| 5001 | `web/publisher_app.py` | 成员工作台，要登录 | 可写（发布日报、同步、配置） |

两个进程共用同一个 SQLite 文件 `web/daily_report.db`。这样拆的好处：读页可以随便投屏、不用登录，
写页必须过登录和 CSRF，权限边界一眼看得清。

## 三、代码脉络：五层，自上而下调用

```
1 入口   start_web.py（一把拉起两站） / web_supervisor.py（守护 + 自愈） / 两个计划任务
2 应用   app.py(5000 只读)  publisher_app.py(5001 路由)  publisher_repo.py(数据层)
3 集成   github_source  feishu_source  email_notifications  report_core / report_quality
4 存储   SQLite 11 张表（publish/commit/feishu/audit/notification…） + uploads/ 照片
5 出口   5000 归档页  gh-pages 静态站  邮件通知  Actions CI/CD
```

讲这一层时强调两条规矩：

- **路由不写 SQL**。5001 端所有查询和视图模型都在 `publisher_repo.py`，路由只负责取参、校验、渲染。
- **采集与业务解耦**。GitHub 和飞书的接口完全不同，但两者都输出「带 member / work_date / summary 的记录」，
  下游不关心数据从哪来——这就是为什么加第三个数据源不用改发布逻辑。

## 四、主线故事：一条日报的 7 步（全场骨架，建议按这个顺序讲）

1. **登录**：`POST /login` → `publisher_auth.verify_password`，口令用 scrypt 加盐哈希，不存明文。
2. **选来源**：`/sources` 把 `selected_source` 记进 session（github / feishu）。没选仓库或群聊时不跳走，
   直接在工作台顶部显示一张引导卡片——这是后来改的，早期强制跳转很打断人。
3. **采集**：`/github/sync` 调 `github_source.collect_last_24_hours`（REST + token + 代理）；
   `/feishu/sync` 调 `feishu_source.collect_feishu_recent_messages`（先换 tenant token，再拉消息）。
   落库靠唯一索引幂等：`github_commits` 用 `(repository, sha)`，`feishu_messages` 用 `message_id`，
   同一份数据同步十次也只有一份。
4. **填表**：`POST /publish` 先用 `report_quality.quality_warnings` 检查填报内容够不够具体（太短会提示），
   再用 `report_core.parse_progress_sections` 拆成「解决的问题 / 完成 / 问题 / 下一步」，写 `published_items`，
   照片按 `uploads/年/月/` 存盘，库里只存相对路径。
5. **统计**：`publisher_repo.workload_series` 按天汇总近 7 天的进展条目，工作台画成柱状图，
   发布时把同一份数据传进邮件，用表格拼出柱状图（邮件客户端不执行 JS）。
6. **简报**：`daily_brief.build_brief` 把正文拆成条目、算出概览（任务 / 完成 / 进行中 / 代码行数 / 工时）、
   自动汇总一句话总结与标签、按模块算改动分布、给出状态与建议；没有数据来源的指标一律不编造。
7. **通知**：`email_notifications.send_progress_email`（SMTP 465 + SSL，支持三档邮件详细程度和附件），
   正文按「概览 → 总结 → 完成 → 风险 → 改动分布 → 明日计划 → 洞察 → 代码改动」排列；
   发送结果逐条写 `email_delivery_logs`；站内还有通知与 `audit_events` 审计（脱敏）。
8. **展示**：5000 端 `/archive` 按日期 + 按人分组，一次把成员发布和 GitHub 提交合并展示；
   `scripts/export_static_site.py` 用同一份数据库导出纯静态 HTML。
9. **上线**：`git push` → CI 跑 87 个测试 → 本机 runner 部署（拉代码、重启、健康检查）→
   Pages 任务把静态站推到 `gh-pages`，公网链接更新。

> 一句话收这段：**采集是幂等的、写入是带校验的、展示是双出口的、发布是自动的。**

## 五、三个设计取舍（最容易被追问，务必主动讲）

**1）为什么不用一个端口做完？**
读写分离换来的是权限边界：5000 可以投屏、给外部看；5001 必须登录。代价是两个进程要一起守，
所以有了守护脚本（见第六节最后一条）。

**2）为什么用 SQLite，不用 MySQL？**
单机、单文件、零运维，事务和唯一索引足够表达「幂等写入」。局限也要主动说：不能多机部署，
高并发写不合适；本项目是「人级」写入频率（每人每天一次），够用。
规避手段是短连接 + `BEGIN IMMEDIATE`（`daily_jobs` 里领取任务时用，避免两次执行同时处理同一天）+ 唯一约束。

**3）为什么单独一层「采集适配器」？**
GitHub 和飞书的认证、分页、字段完全不同，但它们在业务上都是「某人某天做了什么」。
把差异关在 `*_source.py` 里，上层只处理统一形状的记录，新增来源就是新增一个适配器。

## 六、可以主动讲的「坑」（显得是真做过，不是拼的）

- **多图只存一张**：`<label for>` 又包住了 `<input>`，点一次触发两次，第二次把已选文件清空。改成只留包裹。
- **刷新丢草稿**：同步飞书会刷新页面，写了半天的内容没了。改为 `localStorage` 自动存 + `fetch` 只替换活动流水区。
- **Jinja 变量被遮蔽**：`extends` 时子模板顶层的 `{% set %}` 会盖掉 `render_template` 传的同名变量，
  工作区名字一直是空。改名 `workspace_display` 绕开。
- **站点每隔两分钟自己挂**：旧方案用 `cmd` 起 python，控制台被回收时子进程收到 `0xC000013A`
  （STATUS_CONTROL_C_EXIT）静默退出。改为 `pythonw` 守护 + `DETACHED_PROCESS` 拉子进程。
- **每分钟弹一次黑框**：`-WindowStyle Hidden` 只隐藏 PowerShell 自己，控制台仍会创建。
  最终改成 `pyw.exe` 常驻单进程，彻底没有窗口。
- **样式四层叠加互相覆盖**：早期为了「界面太空」追加了 v10 / v10.1 / v10.2 / v10.3 四层，
  同一个选择器被覆盖多次。合并后写了脚本逐选择器比对合并前后的有效声明，确认 0 差异——改的是重复，不是观感。

## 七、演示动线

**5 分钟版（只讲结果）**
1. `127.0.0.1:5001/login` 登录 → 先落到日报归档（`/archive`）→ 点左侧「接入配置」选 GitHub → 进入工作台，指出三个数字：今日提交 / 今日群聊 / 今日已发布。
2. 点「立即同步」→ 活动流水刷新（不整页跳）。
3. 写两句话（解决了什么问题 / 下一步做什么），愿意的话填一个投入工时 → 发布 → 提示成功 + 邮件已发送；
   顺手点开邮件，指出「今日概览」里的任务数、+新增/−删除行数都是从真实数据算的，今天那根柱子也变高了。
4. 新窗口开 `127.0.0.1:5000/archive`，新记录已在。
5. 打开公网链接 `yuuu2026.github.io/Smart-Daily-Report-System` —— 同一份内容，只读公开。

**15 分钟版（补过程）**
- `/sources` 切换数据来源；`/github` 同步单个仓库；`/feishu` 选群聊、切换群聊。
- `/archive` 的分页、按仓库过滤。
- GitHub Actions 两页：CI 的 87 个测试、Deploy 的健康检查，都是绿色。
- `gh-pages` 分支的提交历史 —— 每次发布都对应一次静态站快照。

## 八、预判 8 问，一句话答

| 问题 | 答法 |
|---|---|
| 数据到底从哪来？ | GitHub REST API + 飞书开放平台群消息；两个都支持手动同步，不依赖定时任务 |
| 隐私怎么保证？ | 凭证进 Windows 凭据管理器、`.gitignore` 排除密钥；公开静态站默认不导出成员照片 |
| 多人同时写会不会冲突？ | 写入是「每人每天一条」，冲突概率极低；唯一约束兜底，重复提交只会更新不会重复插入 |
| 接口挂了怎么办？ | 采集失败写 `feishu_sync_runs.error_message` + 审计事件，页面提示「数据不可用」，不阻塞发布 |
| 为什么不用 Django / Vue？ | 规模小、单机部署，Flask + Jinja 概念最少；前端只有三件事（草稿、多图、局部刷新），原生 JS 足够 |
| 代码质量怎么保证？ | 39 个 unittest，push 即跑 CI；发布端按「路由 / 数据层 / 集成」分层，公共逻辑只有一处 |
| 怎么部署？ | `git push` → CI → 本机 runner 部署 → Pages；回滚就是 `git revert` 再 push |
| 有什么不足？ | 单机单用户群、无移动端、无历史统计图表（这三项在 proposal 里就写明不做） |

## 九、如果只有 3 分钟

> 「我们把『写日报』这件事拆成了三段：收、补、发。
> 收——从 GitHub 和飞书自动收集，幂等落库；补——成员只写两句话，系统检查粒度并拆成结构化段落；
> 发——一次发布同时产出本机归档页、公网静态站和一封邮件。
> 代码按五层分：入口、两个 Flask 应用、采集与通知适配器、SQLite、出口。
> 路由不写 SQL，采集适配器屏蔽了数据源差异，所以换数据源不用动发布逻辑。」

## 十、收尾一句

> 「这个项目的重点不是功能多，而是**一条链路真的能跑通**：从别人提交的一行代码，到老师打开就能看的网页，
> 中间没有人工搬运，也没有需要长期维护的服务器。」
