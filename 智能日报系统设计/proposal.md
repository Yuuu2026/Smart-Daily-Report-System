# 项目提案

## 1. 项目目标

把成员发布的工作进展和研发平台中的活动按成员、日期归档，帮助负责人查看每日工作情况。

项目按 PDF 中的「智能日报生成器」案例规划。该案例面向约 5–15 名研发成员及负责人，重点是数据采集、日报整理和定时通知。PDF 未要求 AI 改写、移动端、多团队或历史统计图表。

## 2. 用户与系统

| 用户 | 主要操作 |
|---|---|
| 团队成员 | 登录、发布进展；在分享页触发 GitHub 提取 |
| 负责人 | 按日期查看成员发布内容和 GitHub 提交 |

系统由两个本机网页组成：

- 发布系统：登录后分享工作进展，地址为 http://127.0.0.1:5001/。
- 信息采集与归档系统：按日期查看归档，地址为 http://127.0.0.1:5000/archive。

两套系统共用 SQLite 数据库。成员发布后立即归档；GitHub 提交由登录用户手动提取后归档。

## 3. PDF 项目要求

| 编号 | 要求 |
|---|---|
| R1 | 从 GitHub 或 GitLab 收集提交信息和代码变更统计。 |
| R2 | 从飞书或 Jira 收集当天任务状态变化。 |
| R3 | 按项目关键词提取飞书群聊消息。 |
| R4 | 日报按成员分组，包含代码提交、任务进展、协作沟通三部分。 |
| R5 | 输出 Markdown，并能转换为便于邮件阅读的 HTML。 |
| R6 | 工作日 18:00 生成日报；向负责人发送 SMTP HTML 邮件，向飞书群发送 Markdown 通知。 |
| R7 | 单一数据源失败时其他来源仍可完成；失败项明确显示“数据不可用”；无内容时显示“今日无记录”。 |
| R8 | 五人团队生成日报低于 60 秒；GitHub 限流最多重试 3 次；飞书令牌自动刷新。 |
| R9 | 周末和节假日跳过定时任务。 |

### PDF 明确排除

不做 AI 总结或改写、移动端、历史日报搜索与统计图表、手工增加日报字段、多团队或多租户。

GitHub 仓库配置为 Yuuu2026/Ticketing-System-1-2-task-。成员映射保存在 web/github_config.json；没有映射时使用 GitHub 登录名。公开仓库可匿名读取；私有仓库令牌从本机环境变量 DAILY_REPORT_GITHUB_TOKEN 读取。

## 5. 验收标准

1. GitHub 在指定时间范围内的提交能完整采集，包含说明、作者、提交时间和变更统计。
2. 飞书/Jira 任务状态变化和匹配关键词的飞书群消息能按成员归属。
3. 日报按成员排列，包含提交、任务和协作三个部分。
4. Markdown 能正确转换为 HTML；工作日 18:00 生成并分别发送邮件和飞书通知。
5. 单一来源失败不影响其他来源；失败显示“数据不可用”，空结果显示“今日无记录”。
6. 五人团队的日报生成时间少于 60 秒；GitHub 最多重试 3 次；飞书访问令牌自动刷新。
7. 周末和节假日不运行定时任务。
8. 成员发布内容和 GitHub 提交按正确成员及工作日期归档；重启后仍可查。
9. 重复提取同一 GitHub 提交不产生重复记录；凭据不写入数据库、日志或页面。

## 6. 文档分工

- proposal.md：目标、范围、排除项和验收标准。
- design.md：模块、数据流、接口和关键设计决策。
- data-format.md：输入、存储和输出的数据结构。
- tasks.md：工作顺序、状态和未完成任务。
- 成果列表.md：已完成事项和实际核对结果。

先确认需求，再定数据契约和设计，最后实现任务；未核实的验收项标为“未验证”。
