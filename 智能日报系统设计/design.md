# 系统设计

## 1. 设计范围

系统目标来自项目 PDF「智能日报生成器」案例。当前先运行两套本机网页，完成成员发布、日期归档和 GitHub 手动提取。飞书、Jira、定时日报和外部通知属于后续工作。

## 2. 架构与数据流

目标数据流：

    GitHub / GitLab ─┐
    飞书任务 / 群聊 ─┼→ 数据采集 → 统一记录 → 日报生成 → Markdown / HTML → 邮件 / 飞书机器人
    成员发布系统 ────┘

当前已实现：

    登录分享页 → GitHub REST API → SQLite
    成员发布页 ────────────→ SQLite
    SQLite → 采集归档页（按日期、成员显示）

模块采用单体应用，不拆微服务。当前系统面向小团队和本机使用；按 PDF 的 5–15 人规模，模块边界比分布式部署更重要。

## 3. 应用与模块职责

| 模块 | 职责 | 当前状态 |
|---|---|---|
| 发布系统，5001 | 注册、登录、发布进展；登录后触发 GitHub 提取 | 已实现 |
| 信息采集系统，5000 | 按日期读取成员发布和 GitHub 提交 | 已实现 |
| GitHub 适配器 | 调 API、分页、重试，将提交详情转换为内部字段 | 已实现 |
| 飞书/Jira 适配器 | 获取任务变更和群聊消息 | 待实现 |
| 日报生成器 | 按成员整理提交、任务和协作记录，生成 Markdown/HTML | 待实现完整 PDF 目标 |
| 通知器 | 邮件发给负责人、飞书机器人发给群组 | 待实现 |
| 调度器 | 工作日 18:00 执行并跳过节假日 | 待实现 |

单一职责：数据源适配器只负责采集和规范化；日报生成器只负责整理和渲染；通知器只负责发送。来源之间通过统一数据结构交接，不互相调用内部实现。

## 4. 数据契约

### 4.1 统一记录

- CommitRecord：成员、GitHub 登录名、仓库、提交说明、时间、增删行数、变更文件数、提交链接。
- TaskRecord：成员、任务名称、原状态、新状态、更新时间。
- MessageRecord：成员、发送者、群名、消息内容、时间。
- MemberReport：成员及其提交、任务、协作记录。
- DailyReport：日期、团队名、成员日报、Markdown、HTML。

成员账号跨平台名称可能不同，使用配置映射表统一到系统显示名。无映射时明确使用来源账号名，不猜测归属。

### 4.2 模块接口

    github.collect(repositories, since, until) -> CommitRecord 列表
    lark_tasks.collect(project_id, since, until) -> TaskRecord 列表
    lark_messages.collect(chat_id, keywords, since, until) -> MessageRecord 列表
    generator.generate(members, date, team_name) -> DailyReport
    email.send(report, recipients) -> 成功/失败
    feishu_bot.send(report, chat_id) -> 成功/失败

采集模块返回统一记录列表。生成模块不访问外部平台；通知模块不重新查询数据。

## 5. 时间、存储与去重

- 报告日期和成员工作日按本地业务时区确定；当前 Windows 环境为北京时间。
- PDF 的默认采集窗口为当天 00:00 至任务执行时间；当前 GitHub 手动提取窗口为最近 24 小时。
- GitHub 提交以仓库和 SHA 作为唯一键，重复提取执行更新，不重复插入。
- 成员发布按用户选择的工作日期归档。
- SQLite 当前保存账号、发布信息、GitHub 提交、同步结果及历史功能数据。PDF 目标中的 SQLite 主要用于日报历史。
- 目标部署为 Python 3.11+、公司内网 Docker；当前应用只监听本机回环地址，尚未完成该部署。

## 6. 失败处理与安全

- 每个数据源独立采集。某来源失败时保留其他来源结果，并将失败来源标记“数据不可用”。
- 来源无记录时写“今日无记录”，不省略章节。
- GitHub 遵守 API 限流提示，最多重试 3 次；不可恢复错误写入同步结果并向用户显示简明提示。
- 飞书令牌过期时自动刷新；刷新失败时记录该来源失败。
- 访问令牌从本机环境变量或安全部署配置读取，不写入代码、数据库、审计摘要或错误信息。
- 发布和 GitHub 提取要求登录及 CSRF 校验；密码仅存加盐哈希。
- 日报只整理来源记录，不做 AI 改写或补造内容。

## 7. 关键设计决策

| 决策 | 原因 |
|---|---|
| 先采用单体模块架构 | 团队规模小，数据流线性；微服务会增加部署和排错成本 |
| 为每个外部平台建立独立适配器 | 平台接口变化时不影响日报生成和其他来源 |
| 使用统一记录结构和成员映射 | 合并不同平台数据时保持成员归属一致 |
| 当前先手动提取 GitHub | 已接入 API；定时和节假日策略尚未完成 |
| 将“已实现”和“目标设计”分开标注 | 当前本机发布归档版尚未覆盖 PDF 的全部能力 |

## 8. 当前页面与接口

| 系统 | 页面/接口 | 用途 |
|---|---|---|
| 发布系统 | GET /、/login、/register | 登录后分享工作进展；首页含 GitHub 提取入口 |
| 发布系统 | POST /publish | 保存成员发布内容 |
| 发布系统 | POST /github/sync | 登录后手动提取最近 24 小时 GitHub 提交 |
| 采集系统 | GET /archive?date=YYYY-MM-DD | 按日期查看成员发布和 GitHub 提交 |
| GitHub | commits 列表与单条详情 REST API | 获取提交列表和文件变更统计 |
